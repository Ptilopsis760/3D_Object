## 1. 这条补充对已有结论的影响

### 1.1 碰撞检测方案：无需升级体素层

**之前（20261105.md §2.2、§4 P1）的方向**：三级碰撞检测（AABB → 体素 → 精确距离），以支持空腔嵌套。

**现在**：老师明确说用包围盒计算即可。内部空腔是否能容纳小件，也用包围盒估算，放不进去就跳过。

| 场景 | 之前的计划 | 现在的结论 |
|---|---|---|
| 两个普通模型之间的间隙检测 | AABB 外扩 5mm | 维持不变（已实现）|
| 上盖嵌入底壳的空腔（G1/G2 蜗壳） | 体素化判断真实几何 | **改为：只看 AABB 是否有重叠余量，不做真实几何** |
| 小件放进开口凹槽 | 体素扫掠 + 开放性检测 | **改为：AABB 合法即可，不做扫掠** |
| 取出约束 B 档（6方向扫掠） | 待实现 | **放弃，不做** |

**直接结论**：碰撞检测维持当前的纯 AABB 方案不变，已有代码不需要重构。

---

### 1.2 空间利用率目标：随之下调

体素化碰撞能拿到的利用率提升（嵌套收益）不复存在，目标需要重新校准：

| 方案 | 旧目标（20261105.md §5.3） | 新目标 |
|---|---|---|
| 纯 AABB 碰撞（当前实现） | ≥55% | **≥55%（维持）** |
| 体素碰撞（支持嵌套） | ≥65% | **不做，删除此档** |
| 体素+精确碰撞 | ≥70% | **不做，删除此档** |

**实际可达范围预估**：
- 22 个模型各 1 份，纯 AABB，无嵌套：当前贪心算法跑出 AABB 利用率约 8.56%（分组报告 §4）。
- 多批次复制摆放后，目标区间调整为 **AABB 利用率 ≥55%**，这在纯包围盒框架下通过三阶段算法（贪心 + 模拟退火 + 局部搜索）可以合理期待达到。
- 嵌套带来的理论上限（参考排版 97.6%）在纯 AABB 方案下不可达，不作为目标。

---

### 1.3 成套件预组合：简化判定

20261105.md §5.5 中的预组合判定逻辑（按 AABB 体积比较）仍然有效，但实现目标降低：

- G1/G2（蜗壳底壳 + 上盖）：两个 AABB 有 53~57% 重叠，组合后 AABB 体积下降 17~20%，**值得预组合**
- G3/G4/G5（底座/托盘套件）：组合后 AABB 体积上升 2~6%，**不组合**

预组合不需要体素化验证内部几何是否真的嵌套，只看 AABB 重叠率作为启发式判据。这已经足够。

---

### 1.4 取出约束：只保留 A 档

20261105.md §2.3.2 将取出约束分为三档：

- A 档（禁止完全封闭空腔）：保留，体素化时顺带完成 → **现在改为：在 AABB 判定层面，对完全封闭的几何不做特殊处理，整体当黑盒**
- B 档（6 方向扫掠判定单方向可取出）：放弃
- C 档（任意路径运动规划）：放弃

实际上，纯 AABB 方案下取出约束几乎自动满足：只要模型之间留有 5mm 间隙，在 AABB 层面就默认存在可取出路径。Merge part 整体当黑盒，内部不检查。

## 2. 修订后的技术选型

### 2.1 碰撞检测（最终方案）

```
L1：两个 AABB 各外扩 5mm，判断是否相交
    → "不相交" = 安全，直接通过
    → "相交" = 碰撞，拒绝

仅此一层，不做体素，不做精确三角形距离。
```

已有代码（`CollisionDetector.checkCollision`、`SpaceManager.canPlace`）完全符合，**无需修改**。

### 2.2 空间利用率计算（最终方案）

已在本次修复中实现：按 **AABB 体积**计算，不按真实体积。公式：

```
利用率 = Σ(已摆放模型的 transformedAABB 体积) / 工作空间体积
```

目标值：≥55%（AABB 口径，纯包围盒碰撞）

### 2.3 嵌套摆放（最终方案）

放弃真实几何嵌套。但保留一个轻量的"AABB 内部候选"机制：

- 如果两个模型的 AABB 有重叠（即一个模型的 AABB 部分落在另一个模型的 AABB 内），且实际三角形不碰撞……
- **等等——当前方案连这个都不做**。AABB 有重叠即判碰撞，直接拒绝。

这意味着 G1/G2 的上盖无法嵌入底壳。如果想拿到这部分收益，唯一的路是预组合：把底壳 + 上盖在导入时就拼成一个整体，以组合体的 AABB 作为碰撞单元。

**预组合是当前纯 AABB 方案下获得嵌套收益的唯一手段。**

### 2.4 三阶段算法（维持原设计）

无变化。CLAUDE.md 中的算法架构仍然适用，只是利用率目标数字已更新：

| 阶段 | 目标 |
|---|---|
| 阶段 1 贪心初始化 | AABB 利用率初始 20–35% |
| 阶段 2 模拟退火 | 提升至 45–50% |
| 阶段 3 局部搜索 | 提升至 ≥55% |

（旧目标为真实体积口径的 65%/70%/78%，已作废）

## 4. 体素方案的完整放弃理由（供报告参考）

这里记录完整的工程理由，以便写报告时引用：

1. **内存可行但收益不对称**：5mm 体素下全局网格约 15MB，不是内存问题。问题是收益：纯包围盒方案里 AABB 相交即碰撞，体素化能解锁的"AABB 重叠但实体不碰"的场景在本项目数据中只有 G1/G2 两套蜗壳，用预组合可以等价替代，不需要体素化。

2. **旋转下的重体素化代价高**：每次邻域操作提出新旋转，就需要重新体素化模型（10~100ms），退火阶段的数万次迭代变得不可接受。预计算离散方向可以规避，但那意味着旋转变成离散集合，和"24 种轴对齐姿态"的方案重叠，体素的额外代价不再值得。

3. **空腔识别在本数据集上风险高**：shell_3/4 有 56~75 条开放边（非流形），射线投射法在此类网格上容易出错，需要额外 mesh 修复，超出课设的工程范围。

4. **老师明确说不需要**：最直接的理由。

## 5. 下一步行动

按照修订后的开发计划，下一个实现目标是 **P1：贪心算法支持三轴旋转（24 种轴对齐姿态）**。

目前 `GreedyPlacementStrategy` 只绕 Z 轴转 4 个方向（0°/90°/180°/270°），引入三轴的 24 种标准方向后，同一个不规则零件可以找到占地 AABB 更小的朝向，直接提升利用率。实现成本低（只需扩展 `ROTATION_ANGLES` 为 24 个 `Matrix3x3`），无需改动碰撞检测或 SpaceManager。

## 6. 预组合候选件选型记录（2026-11-06）

### 6.1 问题背景

分组报告识别出 G1/G2（蜗壳底壳 + 上盖）两套成套件：上盖的鼓形部分嵌进底壳的环形腔，两者 AABB 重叠 53~57%，组合后 AABB 体积下降 17~20%。在纯 AABB 碰撞方案下，算法无法把 AABB 相交的模型摆在一起，失去了这部分利用率收益。

预组合是解决这一问题的思路：提前把成套件拼成一个复合件，把复合件的 AABB 作为碰撞单元，这样两个零件就以一个整体的形式摆放，且 AABB 更小。

### 6.2 识别成套件的技术路线分析

**方向 A：人工指定，算法执行**

用户在 UI 端选中两个 STL，标记为组合件，算法只负责把锁定姿态的复合件整体摆放。算法不做嵌套搜索。

优点：实现成本极低，不需要语义推断。
问题：用户必须了解哪些零件是成套的，以及如何摆出正确的嵌套姿态，需要 UI 端提供3D 预览和交互操作支持。

**方向 B：完全不做预组合**

代码里不实现预组合机制，报告里说明理由和理论扩展路径。

优点：零开发成本，专注于已有三阶段算法的完善。
问题：失去 G1/G2 的嵌套利用率收益（约 17~20% AABB 体积）。

### 6.3 为什么自动识别不可行

"成套件"是语义概念，不是纯几何概念。

分组报告之所以能判断出 G1/G2 是蜗壳底壳 + 上盖，是因为分析过程中有多视角渲染 + 视觉语义理解这一步。纯几何算法只能看到"AABB 重叠 53%、实体间距 8mm"，无法推断"这是上盖插进底壳"而不是"两个零件摆放错误"。

三种几何方案各有致命缺陷：

| 方案 | 缺陷 |
|---|---|
| AABB 重叠率阈值 | 误报率高，随机摆错位置也会触发 |
| 体素互补性检测 | 等价于完整体素嵌套方案，已在 §4 否决 |
| PCA 主轴对齐检测 | 只是必要条件，不能区分"成套"和"凑巧方向相似" |

老师也明确指出："在有经验的情况下可以做，但是没有经验的话就不要考虑了。"这里的"经验"指领域知识或对具体文件集的了解，算法本身不具备这种能力。

### 6.4 最终决定：方向 B

**不实现预组合机制。** 具体理由：

1. 多批次摆放（`placeMultiBatch`）已实现，能把利用率从 8.56% 推向 ≥55% 的目标，G1/G2 的额外 17~20% 收益不是必要条件。
2. 方向 A 需要 UI 端支持 3D 预览和组合交互，超出当前 UI 端的工作范围，两端协调成本高。
3. 自动识别技术路线在课设时间线内不可行（§6.3）。
4. 老师定位是软件工程课设，"能做出来就行"，不在核心算法深度上加大投入。

**报告中的处理方式**：在"设计决策"或"未来扩展"章节说明：

> 成套件预组合可以通过用户手动指定（方向 A）来实现，自动识别需要领域语义理解能力，超出本课设范围。完整实现路径为：UI 端提供组合操作入口 → 算法端引入 `CompositeModel` 包装 → 输出时分解为子件各自的世界坐标变换。
